# AGENTS.md

Quick guidance for agents working in this repo. See README.md for what the product is.

## What belongs here

Keep this file selective. Record only technical designs, constraints, and non-obvious details that future work will repeatedly need to use or consider, especially when not knowing them would lead to an incorrect implementation. Do not record every technical detail, completed change, component description, styling choice, or fact readily discoverable from the code. Put implementation history and task-specific detail in design/writeup documentation. Consolidate related rules and remove obsolete or low-value entries instead of continually appending.

## Commands

```sh
pnpm dev          # dev server on 127.0.0.1:5173 (ORIGIN must say so)
pnpm build        # production build
pnpm check        # svelte-check + biome check --write (format included; use for development)
pnpm test         # unit and integration tests
pnpm db:generate --name migration_name  # generate a migration (needs tty)
pnpm db:migrate   # apply migrations
node --experimental-transform-types lab/seed.ts  # works, name tables, scenarios and issues (lab/seed/scenarios.json) into the dev database (DATABASE_URL in the environment wins; production: DEPLOYMENT.md "Loading the content")
pnpm case pull <piece>            # a piece's record into cases/ (git-ignored), its replies into cases/cache (CASE_DATABASE_URL, read only)
pnpm case replay <origin> <piece>|--all|--open  # replay cases on a server with LLM_CACHE_DIR=cases/cache
[COOKIE=…] node lab/patrol.mjs <origin> [path…]   # pages' CSP violations, console errors, exceptions, statuses (before a release, on `node build`)
[COOKIE=…] node lab/frames.mjs <origin> <path> --do "<js>"  # every frame a flow paints and each address it passed through
node --experimental-transform-types scripts/backdrops.ts  # download the backdrop pictures missing from src/lib/assets/backdrops (needs magick)
```

## The rebuild

Version 1.0 was rebuilt from the product's demo (rehearsal-lab `app/`, now an archive); the plan, the data model, the order of work and its state are `docs/design/2026-11-13-step-3-rebuild.md` (§12 is the state). Read it before structural work.

- **The demo is the product.** Its pages, components, copy, colours and motion are the source of truth; match them rather than restyle. Judge looks on the production build beside the demo (`pnpm dev` in rehearsal-lab `app/`, port 4793): the dev server can order CSS differently. Pixel parity is not the goal; no worse experience is.
- **Rendered on the server.** Every page renders on the server and hydrates; the demo's browser storage, its developer settings and the `/lab` pages are gone. Never keep data the server owns in the browser: the browser keeps only the unsent drafts (the home page's, and the sheet's, the plan's and a mail's in `lib/client/drafts.ts`: thirty days, twenty at most, emptied on signing out; never save a draft to the server as it is typed), how the week's glass last moved, the address typed between the auth pages (this tab), and the cookies `lang` (the signed-out pages' language) and `side` (the sidebar folded), which the server reads before rendering.
- **The model layer** came from the lab and lives in its domains: the revision in `server/revision` (`revision.ts` is the server side of one revision), the gate in `server/writing`, collecting in `server/notebook`, translation sources and names in `server/translation`, pure text helpers in `text/`. Every model call goes through a `Caller` (`server/llm/caller.ts`: who pays, the purpose, the revision's background lane, the record), never a global; learners' calls run on their own key only (`server/llm/callers.ts`), the gate's too. Typed choices with probabilities go through `server/llm/decide.ts`: the provider's Decisions API where it has one (`decisions` in `lib/llm/providers.ts`; OpenRouter and OpenAI take different request shapes), else the chat model with thinking off. Thresholds over the probabilities do not carry from one model to another: run `lab/gate-probe.ts` after changing the gate's questions or adding a model. The setup the key form recommends can differ by the language learnt (`RECOMMENDED_FOR` in `lib/llm/providers.ts`): one through OpenRouter keeps the gate on its Decisions API. Language facts code depends on (right to left, written without spaces) live in `lib/constants.ts` and `lib/i18n/langs.ts`, not as language codes in the code that needs them.
- Long-lived callers resolve the learner's key/model for each new call; recording reads the current privacy setting, not the revision's captured one. System prompts may contain learner text: `llm_prompt` is deduplicated per owner and cascades with that account; a record upserts its prompt so the row stays locked until the call commits, and `pruneCalls` skips locked prompts (an ignored conflict would let it delete one about to be named). `pruneCalls` removes calls after thirty days (except a piece's while an open case holds it), then unreferenced prompts; `pruneTapes` gives a finished piece's tape the same thirty days (none when its learner does not help improve Libiamo; an abandoned piece's goes once no case is open), so nothing a learner sees may read the tape after a piece is finished. The admin's sessions never list a learner who does not help improve Libiamo; they hold collecting too, one per reading, from the calls recorded with it (`llm_call.reading_id`, set only to a reading the server has checked is the learner's), and only a reading every call of which kept its words: a call made while the learner did not help still names its reading, and the session would show what they read and kept then.
- **The replay baseline** (`lab/baseline/`, recorded by `lab/record.mjs`) is the model flow's acceptance test: `lab/replay.mjs` plays its sessions against a dev server answering from `lab/baseline/cache` only (`LLM_CACHE_DIR`, `LLM_CACHE_ONLY=1`; `lab/account.mjs` makes the account). Every response must be identical; a difference is a change in behaviour. A prompt changed on purpose means recording the baseline again (about $0.35). Replay on a freshly started server: after a hot update of server modules the dev server can lose `LLM_CACHE_*` (calls then reach the provider on the account's real key).
- From 1.0 the schema changes only by new migrations: `drizzle/0000_init.sql` is what production was created with, and no migration on `main` is ever edited. A branch adds at most one migration before it is merged into `main`: while the branch is open, change the schema and regenerate that one (delete it and its journal entry and snapshot, then `pnpm db:generate --name …` again) rather than adding another; a development database that applied the earlier one takes the difference by hand, with the row in `drizzle.__drizzle_migrations` given the new file's hash.

## Architecture and invariants

### Access

- `hooks.server.ts` decides who may see a page before anything runs: signed out → `/sign-in` (the site's address → `/about`; `/about`, the documents, `/robots.txt` and `/sitemap.xml` answer anyone; only the documents are indexed, `lib/seo.ts`), not set up (`onboarded_at` null) → `/welcome`, `/admin` → 404 unless the role is admin, `/api/*` → 401. Never rely on `redirect()`/`error()` inside a remote query for this: called from the browser it is not honoured (sveltejs/kit#17262).
- Every remote function and endpoint is a public URL whatever page calls it: begin with `learner()` or `admin()` (`server/guard.ts`) and scope rows by the learner's `user_id`.
- Better Auth has no session cookie cache: every request reads the session and user, so settings the app writes hold on the next request. Its `baseURL` is `ORIGIN` alone (it appends `/api/auth`); requests from another origin are refused, so `ORIGIN` must match the browser's URL in development too.

### Data flow

- The app's reads and writes are remote functions (`query`, `command`, `form` in `*.remote.ts`), experimental like Svelte's async mode: Kit and Svelte are pinned to a minor version, and each upgrade reads the changelog's remote-function entries first. Never run two refreshes of one query at once (an older response can overwrite a newer one, sveltejs/kit#17354). `query.live` is not used; the exchange polls (not while its tab is hidden). A page names the queries it opens on in its `+page.ts` (`opening` in `lib/client/refresh.ts`, the browser only): Kit runs it on the hover or touch before a click and waits for it before the navigation, whose view transition freezes the whole screen until the new page is in; a query first awaited in the component is asked for only inside that freeze (a frozen round trip to the server each time, the stall learners far from it felt). What the browser holds shows at once and is asked again once the page is up (`refreshHeld`), or first (`fresh`: review's deck, a reading's marks, the sheet); the pages' last answers are kept for the visit, because Kit keeps one only while something references it and only remote commands refresh what they change (not an endpoint such as `/api/s`, the server's background work, another device). Queries a component awaits that do not depend on each other are awaited in one `Promise.all`: a `$derived(await …)` is not begun until the one before it resolves, and a query is not asked for until it is awaited (Svelte's `await_waterfall`).
- **State that belongs to a learner is per request on the server.** Module-level `$state` in shared code is one object for every request the server renders at once, so a learner's account, settings, pieces or shell state there would render into another's page: make it with `learnerState` (`lib/scope.ts`; `hooks.server.ts` keeps one per request). Module state is fine only for what is the same for everyone (the interface strings, the captcha's site key) or only ever set in the browser (the toast, the tour). Browser APIs (`localStorage`, `matchMedia`, `navigator`, `document`) never run at a script's top level: read them in `onMount` or an effect, and render the server's answer first.
- The root layout's server load gives every page who is signed in (`me`), their shelf of pieces per language (`shelves`: the unfinished, the six most recent, the follow-up, how many are finished), the languages it speaks and the time and time zone dates are shown in; the universal `+layout.ts` loads those languages' strings and pours the rest into `account`, `app` (`lib/account/app.svelte.ts`: settings and look), `writing.shelves` and the clock, on the server and again in the browser. Nothing a page loads may grow with the learner's history: lists (My writing, the notebook, the admin's) come a page at a time (docs/design/2026-11-16-data-reads-by-history-size.md). `<html>` (language, direction, theme, backdrop, the sidebar folded) is written by `hooks.server.ts` from the same setup (`server/account/page.ts`); app.html settles a "system" theme before the first paint. `app.save()` / `app.saveLook()` send settings back one after another and resolve whether the server kept them (say "Saved" only then; a failure is told and the page goes back to the server's); `hydrate()` and `refreshWriting()` ask again after anything that changes them (a sign-in goes home with `goto(..., { refreshAll: true })`).
- **Dates.** Every date a page shows goes through `lib/time/clock.svelte.ts` (the root layout's clock: the moment the page was made and the learner's zone, moved on each minute in the browser): an instant is shown in the learner's zone, a `YYYY-MM-DD` day as it is (`lib/time/format.ts`). Never `new Date()` for a day, `getDay()`/`setHours()`, or a formatter without the zone: the server renders in UTC and the page would change on hydration. The learner's zone (`user.time_zone`, which the server counts days, weeks and reviews in) follows the device (`lib/account/time-zone.ts`). Auth flows call Better Auth's client and return catalog keys for what the page shows. Never pass `callbackURL` where the response is not a redirect the page wants (sign-in): Better Auth's client then loads that page; where a mailed link returns is decided in `server/auth/options.ts`. Signing out and deleting the account leave with a whole page load (`location`), never `goto`, and a 401 anywhere in the browser leads to `/sign-in` the same way.
- The notebook, review and the week are the server's (`lib/notebook/notebook.remote.ts`, `lib/week/week.remote.ts`); pages read them through `notesNow()`, `dueNow()`, `deckNow()`, `weekNow()`, which answer from the tour's sandbox while it plays (`components/tour/sandbox.svelte.ts`: the browser's memory only; it also holds the tour's pieces, readings and week, and nothing it does reaches the server). Notebook queries take the language the page speaks as their argument, so a language switch needs no refresh. A command that changes what a page shows refreshes it in the same response: `week().refresh()` on the server, or `requested(query, n).refreshAll()` for what the client asked for with `.updates()` (Kit 3 fails a requested update the command does not handle).
- The exchange (a scenario's simulated place) is legacy's practice session on new tables: the places in `components/exchange/places` talk to the server only through the `ExchangeApi` the play page builds from `lib/exchange/exchange.remote.ts`, and poll while the cast composes. The cast answers from the agent-reply worker in the server process (`server/exchange/agents`, started in `hooks.server.ts`): batches claimed under leases, lock order exchange → batch → delivery. Everyone who writes in a version's opening must be one of its people (a stray name becomes a second persona the cast voices); passers-by join an open place only when the version's `others` says who may. What an exchange is played in is `settingOf` (`server/exchange/setting.ts`): the scenario and the version in the piece's language, the version's people filled in as the old `counterpartName`/`members`. What a place is told of a failure is a code, never the provider's or the server's words: a refused message is `rejected` with a reason, a failed reply's message carries `failureStop`; no key or a refused key fails at once (retrying cannot help) and the play page says how to fix it. The worker ends expired places on a half-minute sweep, so whatever acts on a place checks `expires_at` itself (`submitMessage` does). The places are fixed at z-index 999: whatever a page shows over one (the toast, a notice) sits above that.
- Scenarios are the server's (`lib/scenario/scenario.remote.ts`, `server/scenario/scenarios.ts`): offered in the language being worked in when published and that version is live (a translation also needs its source in the learner's language, checked or confirmed); the pool's ranking is code. Each language is written on its own: a learner has at most one unfinished piece of a scenario per language (a partial unique index) and its progress is counted per language, so every lookup of a learner's piece of a scenario names the language; a link to a scenario's place, after page or sheet carries the piece's language (`lib/scenario/href.ts`, `?lang=`), which can differ from the one the account works in. What a page receives is built only in `scenarioViewOf`: never a person's notes, `others` or `followed`. Scenarios and issues travel as one content document (`server/scenario/content.ts`, `lab/seed/scenarios.json`). The plan typed on a scenario's page, like the translation sheet's draft, stays on the device (`lib/client/drafts.ts`) and goes to the server with the piece the place or the sheet creates. Something pasted to collect from is kept as a `reading` before anything is highlighted (a scenario's text, before its first phrase is filled in), and opens at `/collect/<reading>`, marking again what is still kept from it (each phrase's `marked` words in its `sentence`); the same words of the same sentence are kept once per reading (a unique index), whatever tab or visit collects them.
- An endpoint whose answer waits on a model (a revision's step, collecting) answers through `keptAlive` (`server/kept-alive.ts`): past 20 seconds the response begins as a 200 and sends spaces until the JSON, so Cloudflare's 100-second limit never cuts it off. A failure is then said only in the body: every failed answer carries `error`, and the browser reads answers with `answered` (`lib/llm/stops.ts`) or the revision page's `api`, never `r.ok` alone.
- The account's picture is Gravatar's, named by the server and loaded by the browser only (`lib/account/picture.svelte.ts`: the initial until it loads within a few seconds); the server never contacts Gravatar, so a slow Gravatar never holds up a page.
- A page loads nothing from a third party but Turnstile, Gravatar and the beacon Cloudflare's Web Analytics injects (a CDN is unreliable in mainland China, and it sees learners' addresses): fonts, data and pictures are Vite assets served from `_app/immutable`. The Content-Security-Policy (`csp` in `vite.config.ts`) enforces it: a new source goes there and into the privacy policy, an inline script in `app.html` takes `nonce="%sveltekit.nonce%"`, and nothing may `eval` (zod runs jitless in the browser, `hooks.client.ts`). Cloudflare's email obfuscation must stay off on every page that renders an address from data (DEPLOYMENT.md, Reverse proxy): it rewrites the server's HTML and the page fails to hydrate. The backdrop's pictures (`src/lib/assets/backdrops`, listed in `server/backdrop/pictures.ts`, public domain or CC0 only) are such assets. The server picks the day's print and painting in the learner's time zone and the root layout hands only those two to the page.
- A translation is written on the device (its draft in `lib/client/drafts.ts`); sending it ("done") creates the piece, which pins its complete assignment in `piece.assignment`: source, original, context and languages, never mutable content-table joins. The send carries the displayed source's generation. Source availability checks the full input fingerprint (`sourceIdentity`: a field added to the version stays out of it while empty, or every source in production goes stale at once); every generator write and admin confirmation is fenced by its generation, including same-content remakes, and an admin's edit is a confirmation under a new generation. Content imports obey the same identity rules. Sources run on the service key with the work's confirmed name table.
- A finished piece's notebook entries come from the notes call after the revision ends; the server retries it (a sweep in `server/revision/store.ts`, `piece.notes_tries`) and after the third failure files what pass 2 reworked as entries without a meaning. The page only watches.
- An unfinished piece nobody will finish is **abandoned** (`abandonStale` every half hour, `abandon` when a revision can no longer be opened): a revision untouched for thirty days or unreadable, a scenario's conversation whose place closed with nothing of the learner's in it (at once) or thirty days ago. Why it is abandoned is checked again in the piece's turn, and never while its revision is in memory (someone is in it). Its revision and tape go; what was written stays, and its page offers to take it up again where it was before its revision (`server/writing/take-up.ts`: own text → a fresh revision, a translation → its sheet, a conversation → the after page).
- Each half of a day (`practice_day`) is written only in the transaction that earned it (`server/week/days.ts` `credit`): the guarded move of a piece to `finished` (`finishPiece`), a write-again, a rating that leaves the queue of its language empty, a visit that finds it empty, the notebook not (`lookAtReviews`). Learning something on a day with nothing to review is the whole day. Days are in the learner's `time_zone`, weeks start on Monday and keep the goal they were held to (`user_week`).
- Review runs on ts-fsrs (`server/review/scheduler.ts`): FSRS-6, steps 1m/10m, relearning 10m, learn ahead 20 minutes (at least the longest step, so an empty queue means the day's reviews are done), review cards due at the start of their local day, new notes from the next local day. The page rates without waiting, from each card's previewed outcomes; ratings are sent one after another. A card blanks the words a model marked in that sentence (`<m>…</m>` in the sentence itself, read by `unmark` in `lib/review/faces.ts`; a separate copied span was miscopied in tests), stored as a span whose pieces apart are joined by "…" and asked as one blank with the words between them given, with where it begins (`note.marked_at`, an example's `at`, a face's `at`; from the tags, the learner's tap or highlight), since the same words can be in a sentence twice; a span is otherwise found as whole words (`spanRanges`); entries without a span fall back to the phrase's fixed words. ts-fsrs 6 needs Node 24 (the image's `NODE_VERSION`).
- The revision's protocol (`POST /api/s`, then `/api/s/<id>/<action>`) stays as the demo had it: it is also the tape, the tour's and `case replay`'s format. `<id>` is the piece's: the page that sends a draft in creates the piece (`lib/session/start.ts`) and opens `/live/<piece>`. What the page opens with is the server's `pageSetup` (`server/revision/handover.ts`), the same for `POST /api/s` and `resume`, never the translation's original; a translation's or a scenario's text, conversation and source come from the database (`pieceId`), and a body that hands them over whole is accepted in development only (the baseline's sessions), so replays run on the dev server. Two actions are not steps and stay off the tape: `progress` (the page's bookmark, kept in the snapshot) and `resume` (where the revision was, for a reload, a restart or another device). Anything the page alone knows that coming back needs goes into the bookmark.
- Revision mutations are serialized per piece; a tape step and its snapshot commit together. A revision already in memory is opened outside that queue, so `resume` and the bookmark never wait behind a step's model call. A learner's revisions leave memory unwritten before their account is deleted (`forgetLearner`), and shutdown always closes the pool. A failed commit retires the in-memory session so later saves cannot persist unrecorded progress. Replaced/dropped sessions lose their callbacks' write authority. Review ratings likewise retain an idempotency key across retries; unconfirmed cards cannot be rated again and pending ratings prevent silent navigation away.
- The tour reads recorded demo fixtures and tapes, never the live scenario pool or learner history. Unmount the previous chapter before replacing its seed, then await settled rendering before continuing (otherwise its awaited derives rebase against the new seed, sveltejs/svelte#18895). Each chapter has a new lifetime: old callbacks must neither enter the next sandbox nor fall through to real requests after exit; a director step stops unless its chapter is the one playing (`live`), never by the run current when it is called. Leave focused tour pages before releasing their sandbox.

### Admin

- The admin pages (`routes/(app)/admin`, English) read and write through `lib/admin/*.remote.ts`, each function behind `admin()`; their server side is `server/admin`. A scenario is saved whole and its versions validated by kind and place (`saveScenario`, which says what is wrong a line each, in the page's words); publishing a translation queues its sources. A published scenario is offered only in its live languages (a version's `draft` hides it) and is refused when none is; a language added after publishing starts as a draft. What waits on the admin (sources to look at, the inbox, open cases) is one query (`waiting`) the commands refresh.
- What learners send (suggestions, feedback) and announcements are tables (§5.3); a learner reads announcements through `lib/account/announcements.remote.ts`.

### Database

- `server/db/schema.ts` follows §5 of the rebuild design: value sets are `text` with a check built from `lib/constants.ts` (no Postgres enums), every time is `timestamptz`, jsonb is validated in code on every write. jsonb written before a field was added lacks it: code that needs the field reads the value through its schema (its default), never by a cast (a scenario's versions and `leaveOut`).
- A race on a unique index inside a transaction is settled with `onConflictDoNothing()`: a caught 23505 has already aborted the transaction. drizzle wraps the driver's errors, so a catch reads the code on `cause`.
- Deleting an account deletes its `user` row: every table that belongs to a learner must reference `user.id` (or a row that does) `on delete cascade`, or deletion leaves their data behind.
- The environment is declared and checked in `src/env.ts` and read from `$app/env/private` (never `$env/*` or `process.env` in app code). Build-time placeholders in the Dockerfile satisfy required variables; add one there when a new required variable is read at module scope.

### Accounts

- Every way a password is set passes Better Auth's `before` hook, which refuses with a catalog key (`auPwShort`, `auPwGuessable`) from `passwordProblem`; pages ask first only to answer sooner. Turnstile guards only the signed-out endpoints, from the `interaction-only` widget in the auth layout.
- Answers never tell whether an address has an account: sign-up, password reset and address changes answer the same either way, and the mailbox is told instead.
- A learner's key is tried before it is saved (one chat request for a single token, `server/account/key-check.ts`; not a Caller call, nothing recorded), then stored AES-GCM-encrypted under `BETTER_AUTH_SECRET` (`server/account/key.ts`) and never sent back to a page.

### Interface strings

- `lib/i18n/catalog/source.json` is written by hand in en and zh-CN; `ui.json` holds every interface language. A new key goes into both, in every language; Vite serves each language as one hashed module (`scripts/vite-i18n.ts`, `virtual:i18n`), so a page's HTML and data never carry strings and the browser keeps each language it has loaded; `test/lib/i18n.test.ts` fails on a key missing anywhere or named nowhere.
- Mails are English (`server/auth/email.ts`) until the catalog has mail strings; without all of `SMTP_HOST`, `SMTP_USER` and `SMTP_PASS` they are printed to the console.

## Implementation conventions

- Imports use the subpath alias `#lib/...` with explicit extensions (`#lib/utils.ts`, `#lib/account/account.svelte.ts`).
- Split code by where it runs (`<domain>/` shared, `components/<domain>/`, `server/<domain>/`, `client/`), then by domain; the domains are in §4 of the rebuild design. "Session" alone is never a name: the auth session, a revision and an exchange are three things.
- Svelte 5 runes only, tabs for indentation. An effect that waits for state to change reads everything it waits on before any early return: in async mode a write made while a page remounts has been seen not to rerun it, and a run that returned early then depends on nothing that can wake it (the tour could not be started again). Svelte component CSS is unlayered and beats Tailwind utilities regardless of specificity: helper classes in `<style>` must not set properties that responsive utilities need to override.
- Fix Biome's findings in the code; a suppression comment says why.

## Verification and documentation

- Agents must not sign their work: no `Co-Authored-By` trailers, "Generated with" lines or other agent attribution in commits, PRs or files.
- Run `pnpm check` and `pnpm test` before finishing code changes. Write essential tests for new TypeScript behaviour; avoid redundant ones.
- Tests mirror `src/` under `test/`. Mock `$app/env/private` with `vi.mock` and a plain object. Test Better Auth behaviour on `better-auth/test`'s in-memory instance with `createAuthOptions` (`test/lib/server/auth/options.test.ts`), not by calling hooks by hand.
- Test semantics, navigation, accessibility, state and data relationships rather than editorial wording; assert exact text only when it is a contract.
- Check flows end to end in a browser against the dev server (or the built image under compose for deployment changes), and record motion when judging it.
- For big changes, use `docs/design/` for the proposed work and important decisions, then `docs/writeup/` for a concise human-readable account of what changed.
    - Design frontmatter: `title`, `type` (bug / feature / ux / performance / accessibility / security / tech-debt / test; may be multiple), `status` (needs-approval → wip → done; only a human may mark done).
    - Writeup frontmatter: `title`, `related-design` (path from project root).
    - Filename format: `YYYY-MM-DD-some-title.md`.
