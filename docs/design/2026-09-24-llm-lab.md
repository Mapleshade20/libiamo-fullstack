# LLM Lab

## Problem

We want to rework several LLM uses (Notes that absorb task-specific details such as "entrar al Nether" instead of the reusable "entrar a"; a feedback flow that walks through the learner's text like a human marker's pen). Today iterating on a prompt means editing code, reproducing the flow by hand, and reading `LLM_DEBUG` console dumps. Concretely:

1. **Only rendered messages exist.** A call site turns structured input (task, transcript, items) into strings and hands them to `chatJson`. Nothing keeps the structured input, so a new prompt version cannot be re-run on past cases.
2. **One case at a time.** Judging a prompt change needs the same 20 real cases run across *before/after × models*, compared side by side and rated.
3. **Outputs are unreadable as JSON.** Notes should look like Notes, annotations like annotated text.
4. **No way to try a change in the real flow** without deploying it for everyone.

Replay/edit-and-replay alone solves none of these. The Lab must not couple product code to tooling or affect learners.

## Decisions

### Recipes: the only product-code change

Every LLM call becomes a declared *recipe* (`server/llm/recipe.ts`):

```ts
export const noteGenerationRecipe = defineLlmRecipe({
	id: "review.notes",
	version: 1,                    // bump when the input shape changes incompatibly
	title: "Vocabulary Notes",
	output: { kind: "json", schema: GeneratedNotesSchema },
	slots: { system: { label: "System prompt", template: `...{{target}}...{{sourceTask}}...` } },
	build: (input, slots) => [...messages],        // pure: JSON-plain input → messages
	options: (input) => ({ temperature: 0.4 }),
	finalize: (value, input) => value,             // pure domain validation / transform
});

const { value } = await runLlmRecipe(noteGenerationRecipe, input, { userId, subjects: { taskId, sessionId } });
```

- **Input is JSON-plain** (no `Date`, no class instances), so it can be stored and re-run. Call sites keep DB reads and side effects (inserting Notes, updating sessions); the recipe is pure. That is what lets the Lab run recipes freely without ever writing domain tables.
- `output.kind` is `json` (schema + `chatJson`, one targeted repair, no truncation repair — unchanged) or `text` (`chatText` + a `parse` function, for XML feedback and plain-text hints).
- `finalize` holds pure validation already done after the call (`validateGeneratedNotes`, `validateGeneration1Evaluation`, diff parsing…), so the Lab sees the same final value and failures as the product. Validation that needs response artifacts for persistence (agent reply target normalization) stays at the call site.
- All 13 call sites migrate. Default output is byte-identical to today; existing prompt tests keep passing.

### Slots

A slot is a named prose template with `{{variables}}`. Code computes the variables (language names, rendered task brief, setting, output shape, per-UI rule text); the template holds the editable prose. Without an override, the template renders exactly today's prompt. An override replaces the template for a whole batch, so a prose change can be tested across a dataset — for example deleting `{{sourceTask}}` from the Notes prompt to test whether the task brief causes leakage.

First version: slots for **Notes**, **feedback annotation** and **agent replies** (the areas under redesign). Other recipes support raw-message editing and model switching only. Unknown variables in an override are rejected; the Lab lists available variables per slot.

### Interception, not coupling

`runLlmRecipe` builds messages, calls the transport (`server/llm/client.ts`, today's `llm.ts`) and finalizes. Tracing and overrides plug in through one optional interceptor installed at server boot (`server/llm/lab/boot.ts`, from `hooks.server.ts`):

- `prepare(call)` → capture decision + the caller's active override (slots, provider, options).
- `record(trace)` → fire-and-forget insert.

Without an interceptor (unit tests, `LLM_LAB=off`) the runner is a plain passthrough. Every interceptor failure is logged and ignored: tracing can never fail or slow a learner request beyond one indexed lookup.

### Traces

`llm_trace` stores: recipe id/version, origin (`app` | `override` | `lab`), the variant used, structured input, final request messages, every attempt (initial + repair: messages, content, finish reason, usage, errors), final value or error, provider (source, model, host — never keys), tokens, latency, and optional subject columns `task_id` / `session_id` / `translation_attempt_id` (plain integers, no FKs).

**Capture policy.** `app`/`override` calls are captured by default for everyone. Only non-admins with a BYOK key see Profile → LLM API Key → "Help improve Libiamo features" and can turn it off (table `llm_trace_opt_out`); without a key the setting is hidden and the opt-out is ignored, and admins are always captured. Opting out stops capture; past traces expire with retention (keys are never stored). Lab calls are always captured (they are the run's results).

**Retention.** `app`/`override` traces are purged after 30 days by the Lab worker. Lab traces live as long as their run. Account deletion cascades a user's traces.

### Staff access

Staff = existing `admin` role. Admins can view every captured trace, use the Lab, and set overrides for their own account.

### Providers

`LLM_LAB_PROVIDERS` (JSON array of `{ id, label, baseUrl, apiKey, model }`, server-only) plus `default` (the environment provider) and `byok` (the acting admin's own key). Lab and override calls routed to an explicit provider **never debit trial quota**.

### Overrides (dogfooding in the real flow)

`llm_override` holds, per admin and recipe, slot templates, provider and options. When enabled, the admin's own real-flow calls use it (`origin: override`); an override with no provider keeps normal routing. Overrides apply only if the user is still an admin at call time. The floating inspector button shows a marker while any override is active.

### Datasets, runs and evaluation

- **Datasets** (`llm_dataset`) target one recipe and carry an optional LLM-judge rubric. **Cases** (`llm_dataset_case`) copy a trace's input (or hand-written JSON) and keep a note. Pinned cases are permanent; when the source learner deletes their account, `source_user_id` is set null and the content is kept (anonymized, stated in the privacy policy).
- **Runs** (`llm_run`) = dataset × variants (label, slot overrides, provider, temperature) × repeats, plus optional judge (rubric overridable per run, judge provider). Each **cell** (`llm_run_cell`) is a job row processed by an in-process worker (`FOR UPDATE SKIP LOCKED`, lease, concurrency `LLM_LAB_CONCURRENCY`, woken on run creation plus a slow recovery scan), mirroring the agent-reply worker. Cells survive restarts; runs can be cancelled.
- **Evaluation**: human 👍/👎 + note per cell and rater (`llm_rating`); LLM judge score 1–5 with rationale (itself the `lab.judge` recipe); per-variant stats (success, repair and failure rates, latency, tokens, mean judge score, votes).

### UI

- `/admin/lab` (admin layout): traces (filter by recipe, user, origin, status), trace detail, playground, datasets, runs, overrides.
- **Playground**: start from a trace, a case or a blank recipe; edit input JSON, slots, provider, temperature — or edit the rendered messages directly for a one-off; run synchronously and compare with the source.
- **Rendering**: system prompts split into collapsible `##` sections, JSON user messages and outputs as structured trees, text as text. Domain renderers where they matter first: Notes as note cards, feedback as annotated messages. Other recipes use the generic tree; more renderers (translation evaluation, eventually the marker pen) are added per recipe.
- **Floating inspector** for admins on every app page, dynamically imported so learner bundles are unchanged: the viewer's own calls on the current task (from the URL), otherwise their most recent calls, refreshed while open, linking into the Lab.

### Code layout

`server/llm.ts` becomes the `server/llm/` folder: `client.ts` (transport, unchanged behaviour), `recipe.ts`, `run.ts`, `providers.ts`, and `lab/` (interceptor, traces, overrides, datasets, runs, worker, judge, recipe registry). Shared pure code (template filling, trace/run view types, stats) goes in `lib/llm/`; components in `components/llm/`. The recipe registry is imported only by the Lab, so product modules never import Lab code.

## Rejected alternatives

- **Langfuse/Helicone as the main tool**: generic traces and playgrounds edit raw messages, cannot re-run through our builders with structured input, cannot render domain outputs, and cannot do per-account overrides. OTel export can be added later on top of the interceptor.
- **Prompts stored in the database**: drifts from git and tests. Winning variants go back into code through a PR.
- **Only raw-message replay**: tests one case at a time.

## Out of scope / later

- Retiring `/translate-eval-live-demo` once the Lab has a translation-evaluation renderer.
- Slots for the remaining recipes; learner-facing view of one's own traces; OTel export.

## Implementation notes

- Ratings attach to traces (`llm_rating`), so a real-flow call and a run cell are rated the same way; a cell's votes are its trace's.
- Lab runs store their trace through an explicit recorder before linking the cell, rather than through the fire-and-forget interceptor, so the cell's foreign key never races the insert.
- Run outputs and judge calls carry `llm_trace.run_id` and cascade with their run (and dataset); every trace without a run (real flow and Playground) is purged after 30 days. Failed judge calls keep their trace id.
- Cells are fenced by a `claim_token` generated on every claim, so a request that outlives a cancel, retry or lease expiry can never write into a newer claim. `attempts` only budgets re-claims.
- Retry re-queues cells that could not run, were cancelled, or whose model call failed (`isRetryableCell`, shared by page and server), replacing their old traces.
- Text recipes are parsed after the transport response is kept, and every failure records its stage (`build`, `provider`, `parse`, `finalize`).
- Runs read case inputs when each cell starts. The UI cannot edit inputs, so a run stays consistent; snapshot inputs into cells before adding input editing (review decision, 2026-09-24).
- Empty provider responses now carry their finish reason and usage. The first real-flow traces showed translation-help expressions returning empty content with `finish_reason: length`: its 1,024-token budget is spent entirely on reasoning by the local reasoning model. Left unchanged here; it needs a decision on the budget.
- Recipes without slots still support provider/temperature overrides and hand-edited messages in the Playground.
- Thinking is on for every call (OpenAI-spec `reasoning_effort`, no provider-specific dialects): each recipe declares low or medium, and every call shares the former largest cap, 32,768 output tokens. The Lab can override the effort in the Playground, run columns and personal overrides (`llm_override.reasoning_effort`).
- `/admin/lab` is now a bilingual (zh/en) guide for admins; traces moved to `/admin/lab/traces`. Lab pages use the Quest Hall's wide measure.
- Capture became default-on (user decision, 2026-09-24): `llm_trace_consent` was replaced by `llm_trace_opt_out`, and the setting moved to the LLM API Key section, shown only to non-admins with a key. The privacy policy paragraph was rewritten; its effective date is left for release.
- Admins can delete traces from the list (selected rows, or every trace the current filter matches) and from a trace page. Run outputs and judge calls are never deleted this way, because their cells would lose their results; they go with their run.
- The Playground opened without a trace or case shows a short guide and the latest real-flow calls to start from.
- Empty temperature fields name the value they fall back to: the recipe's own temperature, or the OpenAI-spec default of 1 when the recipe sends none (`defaultTemperature` on recipe descriptors).
